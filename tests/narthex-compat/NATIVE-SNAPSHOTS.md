# Native snapshots: what changed and why

Every PromQL case selected by `narthex-promql-cases.py` has a `.native.result` next to its `.result`.
The native route produces its own output, so the two files differ. This document records what the
differences are, so a future change can be compared against a known starting point.

Generated by comparing each `.result` with its `.native.result` over the 69 standalone cases.

## Summary

| Class | Cases | Meaning |
| --- | --- | --- |
| identical | 38 | The two files already matched; kept separate so the native run never reads `.result` |
| column name or order only | 26 | Same rows once the header names and column order are set aside |
| number formatting | 3 | `3` vs `3.0`, `31` vs `31.0` |
| one value differs in the last digit | 1 | `simple_histogram`: `0.5500000000000002` vs `...3` |
| real semantic difference | 1 | `scalar.sql`: the native route omits a `count by (...)` group whose value is `0` |

## The differences in detail

### Column names and order (26 cases)

The native route names a computed column after its own tree rather than after the expression, and it
orders columns and rows itself:

```
legacy  | unit | ts | lhs.signum(val) * rhs.val |
native  | ts | val | unit |
```

Every row is present in both; the value and its labels are unchanged. Affected:
`anon_promql_ratio_repro`, `at_modifier`, `computed_scalar_rhs`, `dotted_column_names`,
`float_semantics`, `fused_multi_standalone`, `histogram_multi_partition`,
`histogram_quantile_binary_op`, `math`, `null_samples`, `or_operation`, `scalar_entry`,
`set_operation`, `tsid_binary_join_regression`, `tsid_histogram_quantile_regression`,
`vector_matching`, `common/select/tql_filter`, `common/tql/basic`, `common/tql/case_sensitive`,
`common/tql/matching_filter`, `common/tql/partition`, `common/tql/range`, `optimizer/windowed_sort`,
and the four `EXPLAIN`/`ANALYZE` cases, whose plan text is expected to differ.

The `EXPLAIN`/`ANALYZE` cases differ because the native plan is a different plan:
`FusedSeriesExec` with a `NativeTree` instead of `PromInstantManipulateExec`. That is the point of
the snapshot, not a problem with it.

### Number formatting (3 cases)

`time_fn`, `anon_promql_ratio_repro` and parts of `scalar.sql` print an integer-valued float as `31`
on the legacy route and `31.0` on the native route. Same number.

### Last-digit difference (1 case)

`simple_histogram` at `1970-01-01T00:50:03` returns `0.5500000000000002` on the legacy route and
`0.5500000000000003` on the native route - a float64 sum associated in a different order. This is
below the tolerance the Prometheus comparison uses (`1e-9` relative) and is recorded rather than
normalized away, so a future change that makes it larger remains visible.

### Real semantic difference (1 case)

`scalar.sql` asks for `count by (cpu) (presence_metric)`. The legacy route reports a group with the
value `0` for a `cpu` whose series carry no sample at that step; the native route omits the group.
Prometheus omits it too: `count by (...)` produces a group only where a sample exists. The native
answer is the correct one, and the snapshot records it.

## What is not in here

No case loses rows except the `count by (...)` zero group above. Every other difference was checked
by comparing the multiset of `(timestamp, value, other labels)` rows with the column names set aside.

## Distributed cases

`tests/cases/distributed/**` holds 8 `.native.result` files equal to their `.result`. The native
route needs the standalone server's in-process region transport, so a distributed statement runs on
the existing route. Those files check that switching the native option on does not change a
distributed answer. They are **not** evidence that a distributed statement ran natively.
