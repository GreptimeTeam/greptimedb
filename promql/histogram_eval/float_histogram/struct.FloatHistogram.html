Expand description

A native histogram with absolute bucket counts.

Fields§

§reset_hint: CounterResetHint§start_timestamp: Option<i64>

The start timestamp of the sample this histogram was read from, in milliseconds.

It is metadata of GreptimeDB’s histogram row, not part of the histogram value that Prometheus’s FloatHistogram models. This owned form preserves it – Self::try_from_view reads it off the sample and Self::push_to writes it back – while every operation that derives a histogram from its input (Self::add, Self::kahan_add, Self::mul, Self::div, Self::compact, Self::copy_to_schema, with the constructors beside them) clears it. Self::equals does not compare it.

Both halves are this module’s own policy and say nothing about how Prometheus propagates these timestamps: its FloatHistogram does not carry the field, while its rate and reset evaluation receives start timestamps through a separate channel. This crate’s native range kernel does not read the field; the legacy extrapolation path does, to synthesize a zero point. So a selection that keeps the field preserves what was stored, and does not by itself make a native rate agree with the legacy one.

The positive and negative spans of a histogram read from a view, kept until its buckets change, because Go Equals compares span layouts. Otherwise consecutive indices form one span, the layout Go Compact produces.

pub(crate) fn start_timestamp_reset( current_start: i64, previous_start: i64, previous_ts: i64, current_ts: i64, ) -> bool

The reset a pair of start timestamps witnesses, given the window timestamps they are compared against.

Separate from the payload so a caller whose window timestamps have been moved by an offset can shift the stored timestamps onto the same axis without cloning either histogram: range_eval keeps its samples at timestamp + offset_ms while the stored start timestamp stays where the sender put it, and comparing across those two axes reports a reset for a pair that never restarted.

Source

pub(crate) fn detect_counter_reset_shifted( &self, previous: &Self, previous_ts: i64, current_ts: i64, offset_ms: i64, ) -> bool

Detects a counter reset for a window whose timestamps an offset has already moved.

range_eval hands its windows at timestamp + offset_ms while a histogram’s start timestamp stays on the axis the sender wrote it on, so one of the two has to move. The window timestamps are moved back here rather than the start timestamps forward, because a start of 0 means “the sender stated none” and moving it forward can cancel the offset into a real instant: a start of 2500ms under offset -2.5s would become that 0 and stop being read as a reset. Restoring the sample times keeps the absence meaning what it means.

The subtraction wraps, which is what Go’s int64 arithmetic does and what [crate::range_eval::function::extrapolation_factor] relies on for the same reason: real timestamps are nowhere near the range where the two disagree, and wrapping cannot turn a missing start timestamp into a present one.
