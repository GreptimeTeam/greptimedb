Expand description

The logical plan of one node that runs a compiled native tree.

The node records the query the tree was compiled from, because that text names the value columns it publishes, and it carries the binding the tree’s input was compiled against so the execution plan can be built from it. EXPLAIN shows the compiled tree.

The columns this node produces.

§format: FusedOutputFormat

Fixed output representation, chosen when the node is built.

§canonical_producer: bool

The half of a canonical boundary this node is, if any.

A NativeExpr::Merge collects every fragment of one canonical label set, which a node that runs per scan partition cannot promise in general - and it is why a tree holding one is normally gathered into a single execution. A canonical boundary keeps the query’s width by letting a producer merge what each partition holds and routing the pieces of one label set across partitions; a consumer above it therefore reads whole label sets as ordinary frames. That a node is the producer cannot be read off its tree - the merge is at its root - so it is stated here by the caller that built the boundary.

pub fn serialize(&self) -> DataFusionResult<Vec<u8>>

Serializes the native tree and the binding required to reconstruct this plan node. The PromQL text identifies expression-named output fields; children remain ordinary Substrait inputs.

This is only the node’s own encoding. Whether a planner is allowed to place this node on another machine is a separate decision, made by the planner and the transport, not here.

The envelope is FUSED_SERIES_ENVELOPE_VERSION, the payload’s length in bytes, then the postcard payload itself.

pub fn try_new_canonical_producer( promql: Arc<str>, tree: NativeTree, binding: FusedSeriesBinding, children: Vec<LogicalPlan>, ) -> DataFusionResult<Self>

Creates a producer whose terminal canonical merge is answered per input partition.

The tree’s root has to be a NativeExpr::Merge, because that is the node this flag changes the meaning of: instead of collecting every piece of a label set in one execution, the node collects the pieces its own partition holds and exports one series per label set as a series frame. What that leaves undone - the pieces of one label set that landed in other partitions - is the canonical router’s work above this node, and the caller that builds it is the one that knows the pieces are split that way.

output_schema is the frame the evaluated root declares; it is derived here rather than taken from the caller so the two cannot disagree.

fn with_canonical_router( &self, exec: Arc<dyn ExecutionPlan>, ) -> DataFusionResult<Arc<dyn ExecutionPlan>>

Routes a canonical producer’s frames by label set: the canonical collection step above it.

The producer cannot do this itself.

The producer answers one series per label set per partition: it merged what it found there. The pieces of one set that landed in other partitions are still apart, and every consumer above this boundary reads whole label sets, so they are collected here - by canonical label set, not by matching key, and by the conservative completion contract, because a producer can only promise one series per set per partition and not that each set lives in one partition.

This router is the boundary’s middle stage and nothing else: a query whose tree holds no canonical merge never reaches this code, and a merge that is not a boundary stays where it is.

Source

fn execution_locality(&self) -> InputLocality

The locality this node’s physical execution runs at.

Normally that is the tree’s own classification: a tree that reads across series answers one partition and gathers what it reads. A partition-local canonical merge is the one deliberate exception, and it is a fact about this node’s contract rather than about the tree, so it is read here and not inferred from the root: the caller that built the node knows its inputs are whole per partition, and the merge it ends with collects only that partition’s fragments. Treating every merge as partition-local would instead let a merge that needs every piece run where it cannot see them.

Source

fn output_tags(&self) -> DataFusionResult<Vec<String>>

The label columns of the output, independent of the raw-input binding.

A scalar root has no labels; its one other column is the value. The planner decides them from the whole tree - a match narrows them, or joins both sides’ and a wrapper around either keeps them - and the output schema is where it records that.
