Module series_repartition 

Source
Expand description

Routes evaluated and raw series across DataFusion input partitions.

Canonical routing hashes complete labels; matching routing hashes the evaluator’s own PromQL matching key. Routing groups are not merge identities: evaluated series merge only by exact name and tags. Raw ownership is the complete primary key plus exact label agreement; each input’s complete chain or EOF establishes its contribution to a raw identity for contiguous inputs. An interleaved raw frame here consists of concatenated, independently closed producer chains; identities can recur, but open chains cannot be multiplexed. The owner retains those raw identities until every input reaches normal EOF, then reconstructs contiguous output.

Chains are transported intact to owners with their input-partition ID, followed by one charged normal-EOF message per live output from each completed input. Owners group exact identities and, except for interleaved raw input, may publish an identity as soon as every input has contributed its final chain or normal EOF. Evaluated chunks are decoded only to read routing labels.

§Routing

The key is label_set of the chunk’s metric, hashed whole: coarsening it (a subset of the labels, a metric name alone) would send two label sets to one output for sharing a prefix, which is not the relation a downstream merge groups by. One Routing is built per execution and every chunk is reduced with it, so the destination of a label set cannot depend on which chunk of it was routed first.

The node declares [Partitioning::UnknownPartitioning], never [Partitioning::Hash]: the key is decoded from the rows, and a hash declaration carries an Arrow expression DataFusion could use to prove two plans agree on a partitioning. There is no such expression here, so the claim would be one no optimizer could check and a hash exchange inserted on top of it could silently disagree with. No ordering is declared either: the node reorders, and it says so by claiming nothing.

§Chain boundaries

A consumer of these frames requires a series’ identity not to change and its positions to increase strictly while open, with is_last closing it. An input task therefore assembles each child chain before routing it as one atomic unit. This prevents chains from interleaving during transport; it does not establish the output order or final series boundaries. For a full exact identity (metric name and every tag name/value), the input contract is that each identity closes at most once per input, except for the independently closed chains of an interleaved raw frame. Each owner waits for each distinct input’s final chain or normal EOF before merging a contiguous identity, and for all input EOFs before merging an interleaved raw identity.

What that costs is stated rather than hidden. Nothing of a chain is handed over before the chain closes, so the first chunk of a series reaches its output later than a chunk-at-a-time design would deliver it, and a long chain occupies memory for as long as it is being read. Those bytes are charged to a [MemoryConsumer] as the chain grows, so a pool under pressure ends the read with an error instead of letting a chain grow without bound: the node refuses, it does not spin and it does not buffer past the pool’s limit.

Queues carry whole chains rather than individual chunks, so two sources’ partial chains cannot interleave on one shared output queue; each output needs only one queue.

§Where the reads run

One task per child partition, and no task above them: each input’s task reads its own child, assembles that input’s chains and sends them to their owners itself. No task makes a routing decision for another input, and nothing rotates over the inputs.

That is not an optimisation of the routing: an evaluated partition is one stream whose computation happens inside its poll_next, so a task polling every partition in turn runs the child’s native kernels for all of them itself, one chunk at a time, and the partition count the child declared buys no parallelism at all. It is also what keeps routing local, which is what this node needs when two of them are composed:

  • A partial chain never occupies a shared output queue, so no output waits for a continuation: a chain is either fully assembled in the input task that read it, or not sent at all.
  • A task never waits for another task’s routing decision, and the tasks share no lock while routing, so where one input’s chain goes is not something another input learns or needs.

Producer queues are unbounded: unread owners do not stall routing, but their retained chains continue to consume pool-accounted memory. Owners publish each exact identity after its per-input close/EOF barrier, or all input EOFs for interleaved raw frames, with finality recomputed for that output series.

§Memory, backpressure and end of stream

Output queues are unbounded; each input task holds at most the one chain it is assembling. Every queued chain is admitted through the task context’s pool and carries its charge. The public packed stream releases a completed cursor’s charges after its batch is flushed, while retaining the current cursor’s charges until the cursor is exhausted. The pool controls admission, but queue length is not a constant-byte bound. Owners retain each pending exact identity until its per-input close/EOF barrier is satisfied, then reserve merge workspace for that identity alone. This bounds merge workspace to one pending identity, while its inputs remain charged until handoff. No task waits for memory admission.

An output ends only when every input partition finished and its queue was drained; a chain that closed locally is not the end of anything. Each input sends its own EOF to each live output before recording normal completion. With one task per input the tasks count themselves down: the last records the read outcome, then sender closure lets outputs detect missing EOF or report failure. If the child errors, the failing task records it before cancelling its peers; sender closure makes every output report that recorded error instead of a clean end.

Shared execution records the read outcome before producer senders close, so queue closure together with that shared outcome distinguishes normal completion from a stopped or failed read. A stopped read is missing exactly what it did not route and is reported as an error rather than a clean end.

An output stream owns the read, not the plan it was executed from: DataFusion’s execute_stream_partitioned takes the plan by value and keeps only the streams, so a read tied to the plan would be stopped while its streams are still being consumed. The read therefore lives as long as any of its outputs does, and stops only when there is nothing left it could deliver to: every output was handed out and every one of them is gone. An output that ends - normally, or by being dropped - while another partition was never executed stops nothing by itself, because that partition can still claim its queue; the execution going away as a whole, which no later execute can reach, is the other point at which everything is released.
