Whether this tree can hand over two series that share one canonical label set.

A canonical label set is the identity a NativeExpr::Merge groups by: the metric name plus the ordinary labels, which is exactly what [SeriesLabels] holds. One scan partition holds one series per such set - a stored series is one identity, and the scan splits rows by storage key rather than by label set - so only a computation that writes an existing label can turn two of those identities into one. A label_replace or label_join does exactly that, and it may name the very label that told its input’s series apart.

The rewrite is judged by the labels it writes and the ones its input carries, which is why the caller supplies what it knows about each source’s tags, indexed by the source_index the leaves were bound to: a destination that names no ordinary label of the input writes a fresh one, and a fresh ordinary label cannot make two series equal. That is the difference between label_replace(x, "dst", "$1", "host", "(.*)") - which no merge has to collect - and label_replace(x, "host", "same", "host", ".*"), which folds every series of x into one label set.

A source’s entry is its complete runtime label set, so __name__ is one of its labels whenever its series carry a name - a scan bound to one metric names every series from its binding. That is what makes label_replace(x, "__name__", "same", "__name__", ".*") a rewrite of an existing label: two metrics whose ordinary labels are equal can be told apart by name alone, and rewriting that name folds them into one identity. A name write is collected even when the derived set no longer carries __name__ - after abs, a timestamp or a range function dropped it - because the scan below those kernels can still hold several metrics whose ordinary labels are equal, and writing one name puts them under one identity; the walk has no proof that the input reads a single metric, so the conservative answer is the one that collects.

Everything else either keeps the set it read or answers a set of its own:

  • A map of math drops the metric name, and an arithmetic broadcast does too, but within one metric the remaining tags are the primary key: two stored series of one metric that agree on every other label are the same series, so dropping the name cannot make them one. Each of those nodes hands its input’s answer on rather than claiming one of its own.
  • An Aggregate answers its groups, a Vector that folds series answers its result sets, and a Binary that reads whole vectors files its rows by the label set a sample ends under and refuses two values of a field at one point. A Set does the same, and info merges the results that share a label set. Each answers one series per set it names.
  • A node that hands its input’s series over unchanged - a selection, a window, a timestamp, a parameterized map, topk and its ranking siblings - passes the answer on: an alias below it is still an alias above it.

This is the fact merge_label_rewrites inserts a Merge for: a consumer that reads a whole label set cannot answer from pieces, and this says where pieces of one set can exist at all. A Merge is the collection itself, so it answers false - which is what makes the pass idempotent.
