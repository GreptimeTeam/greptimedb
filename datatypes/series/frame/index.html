Module frame 

Source
Expand description

One Arrow frame family for raw and evaluated series chunks.

A frame carries the same thing whichever sample shape it holds: one row per chunk of one series, with that series’ identity, its finality, its time axis, and one column of samples per logical field. Field names preserve the logical series schema in order. What varies is declared rather than inferred, because the receiver of a frame has no scanner, region, or planning context to infer it from:

ContentIdentityTimeProducer
rawkeytimestampsa storage raw-series scan
rawexplicittimestampsa raw input whose labels are already decoded
evaluatedexplicitgrid_spansa compute node’s evaluated output

Any other combination is rejected here, because no producer can mean it: an evaluated value’s labels may be rewritten by the computation that produced it, so an evaluated frame cannot claim a storage key as its identity, and raw samples have no evaluation grid to be addressed on.

Packing accumulates bounded multi-row batches: SeriesFrameCursor walks one validated chunk and SeriesFrameBuilder emits rows directly as Arrow arrays once a row or estimated byte bound is reached. Decoding reuses one prepared schema per stream through SeriesFrameDecoder. Column layout, metadata, and wire strings stay on the single v1 contract. Raw frames may also declare greptime.series.ordering=interleaved; older readers that do not recognize this ordering reject it. A key-encoded frame declares a versioned LabelDecodeSpec so its labels can be decoded from the received schema alone, and an evaluated frame declares its GridSpec once instead of repeating timestamps.

§Label decode description versioning

The description is one greptime.series.label_decode metadata entry, and remote plans compare greptime.series.* metadata as exact text, byte for byte: a frontend and a datanode that write different text for the same labels disagree about the schema, and the query fails instead of falling back. The rules that follow from that are:

  • A reader rejects a version it does not implement, rather than guessing. This module writes and reads LABEL_DECODE_VERSION only.
  • LABEL_DECODE_VERSION covers the whole text, including each key column’s LabelDecodeColumn::physical_type. That field is a ConcreteDataType, so the text embeds ConcreteDataType’s serde shape: it is not spelled here, and a change in that type’s serialization does alter this text. What keeps such a change from going unnoticed is the frozen fixture tests/compatibility/wire/raw_series_label_decode/v1_physical_types.json, which records the text of every datatype variant and fails the crate’s tests when any of them is serialized differently.
  • Any change to the shape of this text — a renamed or added field, a different ConcreteDataType spelling, a different logical_tags order — is a breaking change at the same version, because it makes two nodes of different builds disagree. Such a change must bump LABEL_DECODE_VERSION and update that fixture with it.
  • The text is canonical: LabelDecodeSpec::canonicalize fixes the only part whose order carries no meaning, so equal labels always write equal bytes.

Deployment rule: during a rolling upgrade a frame may carry a version the receiving node does not implement, and a byte-for-byte schema comparison may fail for that reason alone. The intended behaviour is that such a mismatch disables the native series path at planning time and falls back to the generic path, instead of failing the query at execution.
