MAX_KEPT_RELEASE_BYTES 🔒
Largest segment of release records that recovery keeps from the bytes it read for a footer. It keeps them before it knows which objects are on the chain, so the bound caps what objects off the chain hold until recovery ends; a larger segment is read again if its object is on the chain. A release seals its record at once, so a segment usually holds the records of one or a few regions, 16 bytes each.
MAX_SEALED_BATCHES 🔒
Number of sealed batches that may wait to be created or indexed. One admission can seal two batches, the open batch before an append that would exhaust its positions and the append’s own batch, so the actor admits an append only while two more fit and holds it back otherwise: a stalled object store holds callers back instead of growing the backlog.
MIN_FLUSH_INTERVAL 🔒
READ_PREFETCH_BYTES 🔒
Bytes of decoded segments that all reads of a store together fetch ahead; a segment counts as its length, which bounds its payloads, plus a Record per entry. A read always fetches the segment it yields next, as a read that fetched one segment at a time did, and a later segment only while it fits in what is left, so regions replayed in parallel hold one segment each, up to about max_batch_bytes or more for one oversized append, plus at most these bytes, however many regions open at once. While a fetch copies the payloads out of the downloaded segment it briefly holds the segment’s length once more.
READ_PREFETCH_DEPTH 🔒
Number of segments a read fetches ahead of the one whose entries it yields. On S3 a replay that fetched each segment after the previous one spent about 30 ms per object; with eight fetches in flight a segment arrives about every 4 ms. The segments fetched ahead also take their bytes from READ_PREFETCH_BYTES.
RECOVERY_CONCURRENCY 🔒
Number of objects whose footers recovery fetches at a time. On S3 an object costs two reads, its header and its tail, tens of milliseconds per lane however many vCPUs the node has, and recovery time scales with objects divided by concurrency up to 128 lanes without throttling: at 64 about 10,000 objects recover in about 10 s instead of about 100 s at 8, while the reads use about a third of S3’s request rate per prefix, leaving room for the data file reads of start-up. Each lane holds one RECOVERY_TAIL_WINDOW, 4 MiB in all.
RECOVERY_TAIL_WINDOW 🔒
Bytes recovery reads from the end of an object in one request. The window holds the trailer and the footer of an object with up to 1364 regions of 48 bytes each, so a second request for the footer is rare, and usually the segment of release records, which is the last segment.

recover 🔒
Rebuilds the catalog from object headers and footers, so recovery costs a few small reads per object however large the objects are. Segments are not read, except those of release records, see read_releases; a segment checksum is verified by the read that decodes it. Footers are fetched for up to RECOVERY_CONCURRENCY objects at a time and indexed in sequence order, so the catalog checks the entry ranges of every object against its predecessors like a sequential replay. Only the objects on the chain select_chain picks are indexed.
requires_intervention 🔒
Returns true for an object store error that repeating the request cannot settle until someone changes the credentials, the configuration or the bucket: denied access; an invalid configuration, which is how OpenDAL reports a missing S3 bucket; and a write to a location that does not exist, which is how OSS, GCS and Azure Blob Storage report a missing bucket or container. A read that finds nothing is not one: it is what the read that reconciles a create meets when the object is gone, and a repeat creates it. Every other error, an HTTP 400 or 5xx, a timeout or a refused connection, may pass by itself. A create that fails with an error requiring intervention is still repeated, with the backoff Failing describes.
