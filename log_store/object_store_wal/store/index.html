MIN_FLUSH_INTERVAL 🔒
RECOVERY_CONCURRENCY 🔒
Number of objects whose footers recovery fetches at a time. On S3 an object costs two reads, its header and its tail, tens of milliseconds per lane however many vCPUs the node has, and recovery time scales with objects divided by concurrency up to 128 lanes without throttling: at 64 about 10,000 objects recover in about 10 s instead of about 100 s at 8, while the reads use about a third of S3’s request rate per prefix, leaving room for the data file reads of start-up. Each lane holds one crate::object_store_wal::index::RECOVERY_TAIL_WINDOW, 4 MiB in all.

read_releases 🔒
Reads the release records of the indexed objects, which seed the watermarks of their regions, from the segment of RELEASE_REGION_ID of every indexed object that holds one: the bytes in fetched by object sequence, which the reads of the footers returned, or else one range read. The segments of objects that are not indexed are never decoded. record_skipped_segment 🔒
Records the segment entry describes in the object object_seq as a hole of its region, once per object, counts the skip and warns about it. An object collected meanwhile is skipped without a hole: the catalog is held while the hole is recorded, as a collection holds it while it drops the holes of the object it removes.
recover 🔒
Rebuilds the catalog from object headers and footers, so recovery costs a few small reads per object however large the objects are. Segments are not read, except those of release records, see read_releases; a segment checksum is verified by the read that decodes it. Footers are fetched for up to RECOVERY_CONCURRENCY objects at a time while the listing goes on, and indexed in sequence order, so the catalog checks the entry ranges of every object against its predecessors like a sequential replay. Only the objects on the chain select_chain picks are indexed.
requires_intervention 🔒
Returns true for an object store error that repeating the request cannot settle until someone changes the credentials, the configuration or the bucket: denied access; an invalid configuration, which is how OpenDAL reports a missing S3 bucket; and a write to a location that does not exist, which is how OSS, GCS and Azure Blob Storage report a missing bucket or container. A read that finds nothing is not one: it is what the read that reconciles a create meets when the object is gone, and a repeat creates it. Every other error, an HTTP 400 or 5xx, a timeout or a refused connection, may pass by itself. A create that fails with an error requiring intervention is still repeated, with the backoff Failing describes.

stale_conflict 🔒
Resolves a create of this store’s epoch that met a different object: an object of an earlier epoch can never be on the chain, so the create fails like a transient error; an object of the same or a later epoch belongs to another writer and conflict is returned.
start_epoch 🔒
Writes the empty object that starts the epoch of this instance at object_seq, linked to the recovered tip and carrying the recovered reclaim_boundary, and returns it as the tip later objects extend, together with the sequences of earlier-epoch objects it moved past. The epoch is one above the sequence the create claims, so no two instances share one however their opens interleave, and it is above the epoch of every object recovery listed.
